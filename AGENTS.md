# AGENTS.md

Guidance for coding agents working in this repository. Human-oriented docs are in `README.md`.

## What this is

A template pipeline that converts CSV files to RDF (N-Triples):

```
input/*.csv ──(DuckDB, load-csv.sql)──> xrm-csv-workflow.duckdb
            ──(lib/duck2xrm.js)───────> mappings/sources.xrm      (table/column list)
mappings/*.xrm ──(xrm-cli generate)───> src-gen/mappings.r2rml.ttl (R2RML)
duckdb + R2RML ──(Ontop materialize)──> output/transformed.nt
```

Mappings are written in XRM, a DSL that compiles to R2RML. Ontop reads the DuckDB file via JDBC and materializes the RDF.

## Commands

```sh
./install.sh            # download DuckDB CLI, DuckDB JDBC, Ontop, xrm-cli into bin/ (needs Java 11+, curl, unzip)
./convert.sh            # full pipeline: npm install, db:create, xrm:sources, xrm:generate, rdf:create
```

Individual steps (run from the repo root):

| Script | Does |
|---|---|
| `npm run db:create` | Runs `load-csv.sql` against `xrm-csv-workflow.duckdb` |
| `npm run xrm:sources` | Regenerates `mappings/sources.xrm` from the database schema |
| `npm run xrm:generate` | Validates all `mappings/*.xrm` and writes `src-gen/` |
| `npm run rdf:create` | Ontop materializes `output/transformed.nt` |
| `npm run xrm:bootstrap` | **Overwrites** `sources.xrm`, `vocabularies.xrm` and `mappings.xrm` with a scaffold. Only for starting a new project; never run it on existing hand-written mappings |

Binary paths can be overridden with `DUCKDB_BIN`, `ONTOP_BIN` and `XRM_CLI_JAR`; they default to `./bin/...`.

`db:create` can be rerun: tables and views are created with `create or replace`. Tables or views you remove from `load-csv.sql` stay in the database file, though, and would still show up in `sources.xrm`. Delete `xrm-csv-workflow.duckdb` for a clean rebuild.

## Files

| Path | Edit? | Notes |
|---|---|---|
| `input/` | yes | Source CSV files |
| `load-csv.sql` | yes | DuckDB SQL: one table or view per logical source. Views are a cheap way to split one CSV into several sources |
| `mappings/vocabularies.xrm` | yes | Prefixes, classes, properties |
| `mappings/mappings.xrm` | yes | `map` blocks: subject template, `types`, `properties` |
| `mappings/sources.xrm` | no | Generated by `xrm:sources`; regenerate after changing `load-csv.sql` or the CSV columns |
| `src-gen/*.r2rml.ttl` | no | Generated by `xrm:generate`; committed, and CI fails if it is out of date |
| `xrm-csv-workflow.properties` | rarely | Ontop JDBC settings |
| `lib/duck2xrm.js` | rarely | Schema → XRM generator |
| `install.sh` | for upgrades | Tool versions are pinned at the top |
| `bin/`, `output/`, `*.duckdb`, `node_modules/` | no | Ignored by git |

## Typical change workflow

1. Change `input/` and/or `load-csv.sql` if the data or table layout changes.
2. Rebuild: `rm -f xrm-csv-workflow.duckdb && ./convert.sh`. This also refreshes `sources.xrm`.
3. Edit `vocabularies.xrm` / `mappings.xrm`. Reference columns only via the logical sources in `sources.xrm`.
4. Run `npm run xrm:generate` and fix any errors, then `npm run rdf:create`.
5. Commit the `.xrm` files **and** the regenerated `src-gen/`.

## XRM essentials

Syntax reference: https://github.com/zazuko/expressive-rdf-mapper. Pattern used in this repo:

```
template peopleIRI "http://example.com/people/{0}"

template departmentIRI "http://example.com/department/{0}"

map people from xrm_csv_workflow.people {         // <map name> from <source-group>.<logical-source>
	subject template peopleIRI with ssn;

	types xrm_csv_workflow.People                   // class declared in vocabularies.xrm

	properties
		xrm_csv_workflow.name from name;              // literal from a column
	}

map employee from xrm_csv_workflow.employee {
	subject template peopleIRI with ssn;            // same IRI as in people: both describe one resource

	types xrm_csv_workflow.Employee

	properties
		xrm_csv_workflow.dept template departmentIRI with dept;   // IRI link to another resource
	}
```

- Every class and property used in a mapping must be declared in a `vocabulary`; every column must be a `referenceable` of the logical source.
- The source group name (`xrm_csv_workflow`) comes from the database file name, with special characters replaced by `_`.

## Validation and errors

- `xrm:generate` prints problems as `file:line:column: severity: message` and exits with `1` on errors. Files with errors are skipped, so `src-gen/` can keep stale output for them. Always check the exit code, not only the "Output written" line.
- When many "Couldn't resolve reference" errors appear, look for a syntax error in another `.xrm` file first (for example in `vocabularies.xrm`). It is often listed last.
- All scripts use `set -eu`, so `convert.sh` stops at the first failing step.
- To check the RDF output: `riot --validate --strict output/transformed.nt` (Apache Jena) or `rapper -i ntriples -c output/transformed.nt`.
- To check that a change does not alter the output, compare sorted N-Triples before and after: `sort output/transformed.nt > /tmp/before.nt`, make the change, rebuild, then `sort output/transformed.nt | diff - /tmp/before.nt`.

## Gotchas

- DuckDB table and view names must be lowercase, otherwise Ontop fails.
- The DuckDB CLI, the JDBC driver (`install.sh`) and `@duckdb/node-api` (`package.json`) should be on the same DuckDB release. Bump them together.
- `XRM_CLI_VERSION` in `install.sh` may point to a snapshot pre-release, which is replaced in place. CI keys the `bin/` cache on the jar's release digest for that reason.
- `seq_id` in `load-csv.sql` adds a row number to the people table, because the CSV has no unique key per row.
